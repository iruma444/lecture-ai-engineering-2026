## 宿題

- 取り組んだレベル：発展
- やったこと：
  フロンティアモデルのコーディング・エージェント評価で広く使われている **SWE-bench Verified** を対象に選び、データセットと公式資料を調査しました。
  - データセット URL（Hugging Face）：https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified
  - 公式解説ページ（OpenAI "Introducing SWE-bench Verified"）：https://openai.com/index/introducing-swe-bench-verified/
  - 元論文（Jimenez et al., ICLR 2024, arXiv:2310.06770）：https://arxiv.org/abs/2310.06770
  Hugging Face Datasets から実際の問題文（`problem_statement`）、正解パッチ（`patch`）、評価用テストパッチ（`test_patch`）、`FAIL_TO_PASS` / `PASS_TO_PASS`、人間推定難易度（`difficulty`）を取得し、異なるリポジトリ・難易度にまたがる5件を精読しました。そのうえで、作問・検証に関わった人数とスクリーニング手順、採点方式を調べ、本講義第4回の評価セット（10件）との違いを整理しました。
- 結果：
  1. **読んだ問題5件の要約と難しさの把握**
     - **① `astropy__astropy-12907`（`astropy/astropy`、人間想定時間：`15 min - 1 hour`）**
       合成モデルの入出力の独立性を表す `separability_matrix` で、モデルを並列に結合すると正しい対角ブロックになるのに、入れ子（ネスト）にした途端に独立な線形モデル同士まで非分離（`True`）になってしまう不具合です。正解パッチは内部関数 `_cstack` の1行（計算済みの部分行列 `right` を入れるべきスライスに定数 `1` を代入していた箇所の修正）であり、人間なら再帰処理を丁寧に追えば30分前後で解けます。LLM にとっては修正自体は1行でも、再現コードの行列出力から内部ヘルパー関数のインデックス代入ミスへと原因箇所を特定する探索力が問われます（`FAIL_TO_PASS` 2件、`PASS_TO_PASS` 13件）。
     - **② `scikit-learn__scikit-learn-9288`（`scikit-learn/scikit-learn`、人間想定時間：`15 min - 1 hour`）**
       `KMeans` クラスタリングで同じ `random_state` を指定しても、単一スレッド（`n_jobs=1`）と並列実行（`n_jobs>1`）で結果がわずかに食い違う問題です。並列実行時は事前に `random_state.randint(...)` で `n_init` 個の整数シード配列を作って各実行に渡していた一方、`n_jobs=1` ではミュータブルな `RandomState` インスタンスをそのままループ内で渡していたことが原因でした。乱数状態管理の経験があれば人間でも解けますが、LLM にとっては例外で落ちるバグではなく数値再現性の微妙な分岐差異を見抜き、既存123件の `PASS_TO_PASS` テストを壊さずにシード生成を共通化する点が難しいポイントです。
     - **③ `django__django-12325`（`django/django`、人間想定時間：`1-4 hours`）**
       Django のマルチテーブル継承で親モデルへの `OneToOneField` を2つ（`parent_link=True` を付けた親子リンクと、別用途の参照フィールド）定義した際、フィールドの宣言順序によって `ImproperlyConfigured` エラーが誤発生する問題です。正解パッチは `base.py` と `options.py` の2ファイルにまたがり、メタクラス `ModelBase.__new__` が `parent_link` の有無を確認せずにすべての `OneToOneField` で親リンク辞書を上書きしていた処理を修正しています。ORM のメタクラス初期化順序の深い理解が必要で人間でも数時間かかり、LLM が例外送出箇所だけを局所的に触ると201件の既存モデル検証テスト（`PASS_TO_PASS`）を壊しやすい難問です。
     - **④ `sphinx-doc__sphinx-10323`（`sphinx-doc/sphinx`、人間想定時間：`<15 min fix`）**
       Sphinx の `literalinclude` ディレクティブで `:prepend:` を使うと、先頭のインデント空白が除去されて XML 等の字下げが崩れる問題です。正解は `LiteralIncludeReader.read()` 内のフィルタ配列で `dedent_filter` を `prepend_filter` の前に移動するだけの修正で、人間なら15分未満で直せます。LLM の場合は余計な空白保持ロジックを新規追加するような過剰修正を避け、既存のフィルタパイプライン順序の意図を読み取って最小変更で直せるかが試されます。
     - **⑤ `sympy__sympy-17630`（`sympy/sympy`、人間想定時間：`1-4 hours`）**
       SymPy でゼロ行列 `ZeroMatrix` を含む区分行列 `BlockMatrix` を2乗（`b * b`）すると計算できるのに、3乗（`b * b * b`）して `block_collapse` を呼ぶと例外が発生する問題です。スタックトレースには `blockmatrix.py` が現れますが、真の原因は別ファイル `matexpr.py` の `_postprocessor` が1回目の積の `MatAdd` 評価時に `ZeroMatrix` をスカラーの `0` に潰してしまい、2回目の積で行列の次元属性を参照できなくなることでした。トレースバックに出てこない基底クラスの後処理機構を突き止める必要があり、SymPy の内部設計を知らない人間にも LLM にも非常に難度が高い問題です。
  2. **作成に関わった人数・検証の手順・採点の方法**
     - **作成人数と検証手順**：元の SWE-bench は Princeton 大学らの研究チームが12個の人気 Python OSS リポジトリの実 Issue と解決 PR から **2,294件** を収集して構築しましたが、Issue 文の仕様不足やテストの過剰適合が含まれていました。そのため SWE-bench Verified では、OpenAI と著者チームが実務経験のある **93名のプロ Python ソフトウェア開発者** を編成し、抽出した **1,699件** に対して **1件あたり独立した3名の開発者** が問題文とテストを精査しました。その結果、問題文の仕様記述が曖昧なもの（**38.3%**）や、単体テストが特定実装・例外文言に過剰適合して妥当な別解を弾いてしまうもの（**61.1%**）など、重大な欠陥が見つかった **68.3%** を除外し、公平に解けると確認された **500件** だけを残しています。
     - **採点の方法**：LLM 採点や文字列一致ではなく、対象コミット時点の環境を再現した隔離 Docker コンテナ内でモデル生成パッチと評価用 `test_patch` を適用してテストスイートを実行する **決定論的なテスト実行採点** です。バグ再現テスト（`FAIL_TO_PASS`）がすべて通り、かつ既存の回帰テスト（`PASS_TO_PASS`）もすべて通った場合のみ合格（Resolved）となります。
  3. **今日の演習の評価セット（10件）との違い**
     - **規模と品質保証コスト**：演習の評価セットは講師1名が正常系と代表的なエッジケースを10件に凝縮して作成した開発初期向けセットであるのに対し、SWE-bench Verified は実世界の2,294件から93名の専門家が「1件3名レビュー」で68.3%を削ぎ落として500件を作っており、「評価問題と採点テスト自体の正しさ」を担保するために多大な人間コストをかけています。
     - **採点方式の対比**：演習セットは自由記述の自然言語回答を測るため、形式面の「第N回」（コード判定）と意味面の4基準（`rubric.md` による LLM-as-a-Judge ＋ `unsure` の人間確認）を組み合わせています。一方 SWE-bench Verified は単体テストの実行結果だけで100%機械的に合否が決まるため採点時の LLM の揺れはありませんが、その分「単体テスト自体が実質的なルーブリック」になります。
     - **基準の更新可能性**：開発中の自社・講義用評価セットは演習 STEP 3 のように `unsure` や不一致を見ながら後から `rubric.md` を1行ずつ改善できますが、公開ベンチマークはスコアの比較可能性を保つために後からテストを気軽に変更できないため、公開前の厳格な人間スクリーニングが不可欠である点が大きく異なります。
- 気づき・疑問：
  SWE-bench Verified の人間監査で除外理由の6割以上（61.1%）を占めたのが「単体テストが特定の実装やエラー文言まで決め打ちしていて、別の正しい実装を不合格にしてしまう問題」だったという事実に強く納得しました。これは演習の `#07` で、内容としては適切な拒否応答（「関係する回：なし」）が正規表現コード判定（`第N回` の有無）によって機械的に `fail` になった現象とまったく同じ構造です。「LLM ジャッジは曖昧さで揺れやすく、コード・単体テスト判定は硬すぎて妥当な別解を弾きやすい」というトレードオフは、10件の小規模評価でも500件のフロンティアベンチマークでも共通する評価設計の核心だと感じました。また近年は SWE-bench Verified でも訓練データ汚染（記憶）が課題になっていると聞くため、今後はプライベートリポジトリや動的に生成・更新される評価セットをどう低コストに維持するかが重要になりそうだと思いました。
